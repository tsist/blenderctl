# 自我改进协议

在真实任务出现新发现、反例、用户纠正，或准备改变既有方法时读取。目标是让下一次决策更可靠；不以新增条目数或更新频率衡量进步。

## 证据如何变成指导

| 状态 | 含义与使用限制 | 下一步 |
|---|---|---|
| observation（观察） | 单次结果、反馈或待解释现象；留在本次实践记录 | 找出影响决策的条件，排除明显混杂因素 |
| candidate（候选） | 有可说明的判断和至少一个可回读实例；不是默认做法 | 在匹配任务中明确作为假设试用，安排能推翻它的观察 |
| validated（限定验证） | 在明确边界内获得足够的运行与结果证据 | 只在该边界内推荐，继续记录反例 |
| challenged（受质疑） | 新反例或环境变化削弱了原有结论 | 停止将其作为默认建议，缩小适用范围或重验 |
| retired（退役） | 已被更可靠方法取代，或无法在合理范围成立 | 从默认路线移除，保留被替代原因与证据指针 |

状态不是只升不降。过期版本、不再可回读的证据、无法复现的结果应触发范围复核。`validated` 永远不代表适用于所有 Blender 任务。

候选只需一个可回读实例和一个明确、可被推翻的决策假设，可以来自失败或部分结果；不能因此宣称该方法有效。以下条件用于首次晋升为 `validated`，不用于阻止记录候选：

1. 明确适用输入、用途、约束以及不适用情况，能够告诉执行者何时改变决策。
2. 实际产物按其用途通过验收，技术检查、视觉观察与用户反馈不互相冒充。
3. 有足以检验迁移性的证据。通常来自另一输入、另一次任务或有意义的受控复验；同一文件原样重复运行只能支持复现，不能支持泛化。
4. 考虑至少一个会让该方法失效的条件，并检查与现有规则是否冲突；记录剩余未验项。

证据需求随结论强度变化：单次确定性复现可以证明某个狭窄故障确实存在；开放式“普遍更好”的制作建议需要更广证据。用户对一件作品的认可只支持这件作品及其偏好，不自动证明方法普适。

## 每次实践的改进循环

1. **提取差异**：预期与实际哪里不同？哪一个决策造成质量、返工或运行成本变化？没有新发现就不改。
2. **解释原因**：区分输入、方法、操作实现、环境版本和审美目标。工具偶发失败或未控制的多项改动，不足以证明工作方法错误。
3. **提出最小修订**：写成“在条件 X 下，优先做 Y，用 Z 判断继续；若 W 出现，改用另一方案”。避免只写“以后注意”。
4. **验证修订**：对受影响决策做有针对性的复验；改变通用主流程时，还检查另一类任务是否受到不必要约束。文档情境演练只验证措辞与决策，不算 Blender 生产证据。
5. **主线程审核并串行落盘**：核对证据、边界、授权和非目标保护，更新技能、索引和版本；保存差异与回退依据。子代理只能按本次委派范围行动，技能中的持续改进授权不改变只读委派权限。
6. **同步状态**：WM 保存本次结果与下一验证动作；只有跨会话稳定结论进入长期记忆，必要时把项目知识写入 Wiki。

针对技能本身的问题也执行这个循环：过早细化、重复询问、误用旧经验、加载太多无关材料、漏看最终画面等，都可以成为候选改进，但需要对应的具体行为证据。

## 方法条目的最小格式

有真实候选后才新增 `references/methods/<主题>.md`，并加入[方法索引](method-index.md)。相邻问题优先合并，不预建空领域文档。每个条目只承担一个可说明的决策。

```yaml
id: BM-YYYYMMDD-short-topic
status: candidate
claim_type: workflow  # workflow / aesthetic-preference / environment-specific
applies_when: "输入、用途、交付约束及需要该决策的信号"
avoid_when: "已知不适用或证据不足的情况"
decision: "优先做什么，为什么，什么情况下改道"
checkpoint: "决定继续、修正或停止的可观察结果"
evidence: []
evidence_status: "历史候选指导；原始工程证据未公开，需独立验证迁移"
counterevidence: []  # 无已知反例时说明尚未覆盖的边界，不虚构反例
scope: "Blender/工具版本敏感范围、资产与任务范围"
last_reviewed: "YYYY-MM-DD"
supersedes: null
```

模板字段用于表达证据，不是照抄空白的产物。必要说明写在 YAML 后，命令细节链接到操作层。候选发布前 evidence 至少有一个真实实例；如果只有想法，留在 WM 的验证计划里，不伪装成经验。

## 修改、验证与回退

- 修改前读当前文件；在本次审计目录保存将修改文件的前版本和 SHA，避免覆盖其他会话的后续更新。写入前再比较源 SHA；已变化时重新审阅合并。
- 只改能被本次证据解释的部分。术语澄清和小缺陷递增补丁版本；工作决策或结构变化递增次版本；重大不兼容边界变化再考虑主版本。版本号记录变动，不代表质量评分。
- 更新方法索引及关联引用；同一问题优先修订已有条目，避免新旧建议并存却未说明关系。
- 运行可用的技能结构校验，并核对新增链接、适用边界和情境行为。涉及实际 Blender 方法效果的结论，追加真实运行与观察证据；没有证据时保持候选。
- 审计目录记录修改原因、前后版本、变更文件、验证结果、未验项及恢复入口。需要回退时先核对当前 SHA；已有后续修改则逐项撤回，不能直接用旧备份覆盖。
- 用户指定的个案例外可直接按当次目标执行；是否改变默认指导仍按证据判断。用户纠正是重要输入，不应机械泛化为所有人的审美或所有资产的规则。

自我改进在执行实际任务和复盘时触发，不等于后台定时运行，不另建自动化。低置信候选不自动成为默认建议；技能也不自行扩大权限、重写核心规则或降低安全约束。
