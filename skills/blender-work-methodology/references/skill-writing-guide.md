# 技能写作规范

写技能，是给同行留一份工作笔记。读的人懂 Blender、手头有活，想马上知道下一步做什么、为什么这么做。

## 六条规矩

1. **像带徒弟的师傅说话。** 先说做什么，再用一句说为什么。
   > 白模先给用户看，再展 UV。形体一改，UV 就得重展。

2. **只写该做的动作。** 安全要求也写成动作。
   > 原：不得覆盖源文件。
   > 改：在工作副本上改，源文件留着对照。
   >
   > 原：打开成功不代替渲染验收。
   > 改：重开之后渲一张图，看效果对不对。

3. **一段讲一件事。** 短句，动词开头。一句超过四十个字就拆开。

4. **用行业里通用的说法。** 白模、卡线、控制笼、展 UV、烘焙、蒙皮、权重、镜头表、粗剪。代码标识符只在读者需要敲进去时出现，用反引号包起来。

5. **正文只写现在怎么做。** 日期、批次号、版本流水、验收经过和证据路径，放到 `references/sources.md` 或文末「参考」。版本号只在 AGENTS.md 和 blender-cli 各写一处，其余地方需要时用 `discover` 实时查。

6. **附一个从头走到尾的小例子。** 接到什么、做了哪几步、交出什么、谁来看。

## 技能的骨架

```markdown
---
name: <技能名>
description: <一句说做什么>。<一句说什么时候用>。
---

# <标题>

<一段：本技能负责什么，属于哪个部门，链接部门卡。>

## 怎么做
<按制作顺序写步骤。>

## 交给下游
<交什么、下游怎么检查。>

## 例子
<一个完整的小例子。>

## 参考
<references 里的文件，以及 sources.md。>
```

description 写给路由看：读者凭这两句就能判断该不该打开这个技能，所以要具体。

## 写完自查

- 新人只读第一段，能说出这个技能管什么吗？
- 每一段都有一个能马上执行的动作吗？
- 搜一遍「不等于」「不证明」「不代表」「不得」「严禁」「禁止」「不能」「仅」，每一处都改成了该做的事吗？
- 正文里还有日期、批次号、SHA、审计路径吗？
- 留下的命令和参数，用当前 CLI 的 `discover` 或 `--help` 核对过吗？
