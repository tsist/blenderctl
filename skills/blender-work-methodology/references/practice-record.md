# 实践记录与方法沉淀

做完一件有挑战的作品、踩过一个值得同行避开的坑，或者用户指出了原先做法的盲点时，按这份轻量结构把经验留下来，让下一次决定更准。

## 一次实践记哪四段

把完整记录存在当次任务的 `work/audit/<batch>//practice.md`，Working Memory 里只记一句话摘要和路径。日常小改只留目标、前后对照图和结果就行。

1. **交付目标与起点**：用户拿这件作品干什么用、哪些地方固定要保住、起手用了哪个工作副本和哪些已有方法。
2. **改变决定的那几轮调整**：只记真正让你换做法或锁定参数的回合，对比时保持同机位、同灯光、同帧位。

   | 当时卡在哪 | 改了什么 | 画面或数据发生了什么变化 | 下一步决定 |
   |---|---|---|---|

3. **验收结果**：把技术检查、视觉对照和用户的实际评价分开记清，标出 `pass / fail / not_run / not_applicable`。
4. **要不要更新技能**：提炼成一句可操作的判断——「遇到情况 X 时，先做 Y，看 Z 确认过关；要是出现 W，就改走另一条路」。

## 一条经验怎么晋升进方法表

每条经验按证据厚度标五个状态，证据变了随时升降：

| 状态 | 什么时候用这个标签 | 怎么对待它 |
|---|---|---|
| `observation`（观察） | 单个任务里刚碰到的现象或猜想 | 留在当次审计记录里，下次遇到同类活留心核对 |
| `candidate`（候选） | 至少有一个可回读的真实案例支撑，说得清什么时候该这么做 | 收进 [method-index.md](method-index.md)，遇到同类任务拿出来试用 |
| `validated`（已验证） | 在两件以上不同输入的作品里都跑通，且摸清了它的失效边界 | 作为该场景下的推荐做法 |
| `challenged`（受质疑） | 新作品或新版本里出现了反例 | 缩小它的适用条件或重新验证 |
| `retired`（退役） | 已有更稳当的新工具替代 | 从主路线撤下，在 `sources.md` 留一行备查 |

## 新增方法卡片的头部格式

有真实案例支撑的新候选，在 `references/methods/<主题>.md` 建一张短卡片并登记到 [method-index.md](method-index.md)：

```yaml
---
id: BM-YYYYMMDD-short-topic
status: candidate
applies_when: "什么样的输入、用途或故障信号下用它"
avoid_when: "哪些场景不归它管"
decision: "先做什么，为什么，看到什么信号就换路线"
checkpoint: "怎么亲眼确认这一步做对了"
last_reviewed: "YYYY-MM-DD"
---
```

改技能文件前先读最新原件，把备份存进审计目录，改完跑一遍链接检查并运行同步脚本更新镜像。
