# 最高工作指导：优先插件配合CLI完成多步工作

本包保留插件/CLI优先的工作方法，具体能力与提效实证另行判断。用户当前要求和更高层规则优先；[完整工作单元与效率](efficient-work-units.md)是其下的次级指导，不能由此要求无收益安装/开发。

## 先判断可封装的工作单元

每次开始或调整路线，先列出本轮输入、连续操作、可观察结果与恢复点，检查适用的已安装/已授权Blender插件及其CLI接口。优先由插件完成有关联的多步操作，由CLI统一调度，减少代理逐项工具往返及一次性脚本重复。批次内部保留阶段检查点；“一次完成多步”不等于跳过参考、缩略图判断或最终实际观察。

选择顺序：合适的现有插件与CLI接口 → 现有插件适配CLI → 在已授权范围开发可复用插件/适配器。若当前只是单步、无适用插件、接口依赖GUI或开发成本明显高于收益，记录具体原因后使用现有CLI/MCP最小操作；下次遇到可复用多步工作重新优先评估插件。不要为满足形式而安装或开发无收益插件。

## 职责与批处理契约

- **插件**承载领域逻辑、连续步骤、参数与可检查的阶段结果；优先让GUI和后台调用同一核心逻辑。实际operator/data API及上下文要求按版本验证。
- **CLI**绑定源/资源/插件版本，组织参数、作业、批量、检查点、日志/回执和恢复；成功产物有明确持久路径。
- **代理**决定目标与质量、调用原生生图等宿主工具、准备输入清单、看实际结果并调整。Blender插件不能伪装调用不存在的原生生图API。
- **MCP**承担确需实时会话的发现、GUI相关交互与观察，换入口通过持久快照和新状态核对。

工作单元至少说明输入与依赖、对象/共享数据影响、参数、输出、逐阶段成功条件、失败停点和恢复方式。批量执行隔离各候选/输出，不并发写同一工程；复用绑定原manifest/版本/SHA。保存成功后独立重开并观察真实输出。

## 引入或开发插件的步骤

1. 先明确用户目标、当前重复成本及插件适用性，核对现有插件来源/版本、许可、后台兼容性和实际接口。
2. 功能需求不清时在任务开始后逐项询问并记录选择。当前用户已明确的需求不重复访谈。
3. 做最小真实纵向工作单元：输入→插件执行→CLI回执→候选保存→运行时验证→实际观察。通过后扩成批处理；先保证结果再量化效率。
4. 比较相同质量条件下的往返次数、人工介入、耗时、重复成功率与错误恢复成本。只减少调用数不能证明作品或效率通过。
5. 验证来源/环境兼容与任务授权后采用；安装/启用/全局偏好变更按现有授权处理。保持源副本、检查点、持久依赖和回退依据。

当前配套CLI0.54.1/插件0.7.0提供run/batch/study/template-save；材质仍为standalone。参见[材质操作](../../blender-material-authoring/references/pbr/plugin-cli-authoring.md)。完整私人需求访谈和基准未发布，不能作为新任务批准或提速保证。

## 材质制作的协作边界

转[材质技能](../../blender-material-authoring/SKILL.md)并读取其[PBR规范](../../blender-material-authoring/references/pbr/framework.md)。原生生图优先制作所有空间图层/复杂遮罩；插件+CLI负责导入、映射、节点、参数、批处理和验证。只有简单渐变/数学依赖遮罩可在Blender生成；不能用插件程序纹理改变既定制作来源。
